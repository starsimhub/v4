Architecture

🧠0% 🤖100%

This section explains how Starsim is put together and why. It is for two kinds of reader: a modeler who wants to know what happens when they call sim.run(), and a prospective contributor deciding whether this is a codebase they could work in. You don’t need any of it to use Starsim; the rest of the user guide, starting from What is Starsim?, is the place for that.

The idea in one paragraph

A model in Starsim is written once, as data: states (S, I, R = ss.states('S I R')), transitions between them (S >> I @ beta * I), and parameters, with the mixing, demography and interventions around them. Each disease checks its own structure when it is made (unknown names, rates of the wrong shape). When the sim is initialized, Starsim reads those objects, fills in what was left out (and records each guess), checks them against each other, and chooses how to run them: as a deterministic ODE, as one of three stochastic compartmental solvers, or as agents. Because the model is data rather than code, everything else is derived from the same objects: the printed description, the equations, the diagram, and the exports to other frameworks. One declared model, several ways to run it, and one source of truth for all of them.

A model can also be written as code, as classes with their own step() methods: these run through the same loop, as agents if they keep a value for each person and otherwise with no agents at all (an ODE of your own runs as just that), and can sit beside declared models in one sim. Modules covers how the two kinds fit together.

The principles behind it

Every design choice is checked against a short constitution. In order of weight:

  • Simplicity. Writing and changing a model should be easy for an epidemiologist, not just an engineer. A model ported to Starsim should get shorter.
  • Performance. As close to custom compiled code as is feasible. This is why compartmental runs go through kernels (small compiled functions that step the compartments) and why agents use compiled passes over their arrays.
  • Flexibility. Every major modeling feature should be expressible, even if not every one is built in. When a declaration can’t say something, a module’s step() can.
  • Correctness. The machinery is validated by tests, but over-correctness should not cost simplicity or speed: Euler steps, Erlang stages and other standard approximations are fine, as long as they are announced.

After these come understandability (few concepts, no brittle subsystems), maintainability (solvers should not each reimplement the same thing), composability (use as much or as little of Starsim as you want), short startup (no long compilation before a small run), and being easy for AI tools to work with. The development principles add: no legacy shims, avoid bloat, and think about the whole system before adding a special path for one case.

You’ll see these principles in specific choices throughout this section. For example, solver='auto' picks the simplest representation that runs the model faithfully (simplicity, performance); every approximation prints one line saying what was done (correctness without refusing); and the compiled kernels are optional, with a plain-Python path for short runs (short startup).

The map

Starsim has five layers. Broadly, each builds on the ones before it, and a contributor can usually work in one layer at a time.

Layer Files in starsim/ What they do
1. Declaration transitions.py, internals/expressions.py, internals/graph.py, internals/parameters.py, distributions.py, internals/dists.py, internals/time.py, internals/dates.py, internals/conditions.py, internals/dimensions.py, strains.py The words a model is written in: states and transitions, rates as expressions (beta * I), parameters (ss.par, ss.by), durations and rates with units, conditions for where=, stratifications and strains. internals/graph.py collects one module’s declarations into an ss.graph.Graph, names them, fills in defaults (recording each guess), and checks them.
2. Build and orchestration sim.py, internals/loop.py, internals/timeline.py, internals/modules.py, people.py, internals/arrays.py, networks.py, diseases.py, demographics.py (including ss.Pregnancy), interventions.py, products.py, connectors.py, analyzers.py, results.py, run.py The runtime objects. sim.init() builds the population, the modules and the results, and chooses the solver; the loop then calls each module in a fixed, printable order each step. ss.Module is the one base class for diseases, networks, demographics, interventions, connectors and analyzers. run.py runs many sims (ss.MultiSim, ss.parallel).
3. Engines solvers/choose.py, solvers/engine.py, solvers/compartmental.py, solvers/mixing.py, solvers/agents.py, solvers/crossing.py, solvers/deliveries.py, solvers/particles.py How a graph is run. choose.py picks the solver and says why. Each declared module gets one engine: Compartmental (which flattens the model into a program of flows that the kernels step) or Agents (boolean arrays over agents). crossing.py tracks several diseases jointly when one refers to another’s states.
4. Speed and alternate backends solvers/backends/ (kernels.py, ode.py, draws.py, passes.py, rust.py, jit.py, cache.py, memory.py), internals/gradients.py, and the Rust crate in solvers/rust/ The same runs, faster or differentiable. kernels.py holds the Numba kernels that step a compartmental program (ss.kernels), and ode.py the same ODE in NumPy for runs too short to compile for; draws.py the exact random draws everything shares; passes.py the compiled passes over agents and network edges; chain.py the chain binomial and tau-leaping in JAX; rust.py swaps in the Rust copy of all of these; jit.py is ss.jit, for compiling users’ own code; and internals/gradients.py runs the ODE in JAX for gradients and many runs at once. No user needs to read these.
5. Edges fit.py, internals/display.py, internals/errors.py, geo.py, data.py, converters/, library/ What builds on a run model. Fitting (sim.fit()); describe(), diagram() and equations(); errors, warnings, and notes; places, mobility and data by place name; importers and exporters for other frameworks; and example diseases and networks (import starsim.library as ssl).

Helpers that every layer uses are in settings.py (ss.options), utils.py, internals/debugtools.py (profiling, debugging, and mock objects for tests) and internals/cli.py (the starsim command). Everything in internals/ is also at the top level: ss.graph, ss.expressions, ss.gradients, ss.errors, and so on.

For a sense of scale, the package is about 70,000 lines of Python: about 13,500 in declaration, 19,000 in orchestration, 12,500 in the engines, 8,000 in the speed layer (2,700 of them the Numba kernels), 15,000 at the edges (half of that in converters/, and 3,000 in library/), and 2,000 in the helpers. The Rust copy of the kernels adds another 7,000 lines, outside the installed package. The core that a model passes through on every run is layers 1 to 3.

A few things to notice in the map:

  • A declaration doesn’t say how it will run. The states, transitions and parameters of layer 1 are the same objects whether the model runs as an ODE or as agents; only when they are evaluated (a rate, a condition) do they see one value per group or one per agent. That is what makes the solver a choice rather than part of the model.
  • Every compartmental solver steps the same program. The ODE, the chain binomial, Gillespie and tau-leaping all run the flat list of flows that Compartmental builds. The JAX backends, the Rust kernels and the particle filter run that same program too, so a fix in one place is a fix for all of them.
  • Code is never analyzed in advance. A function in a rate, or a module’s step(), is simply called with what the solver has (one value per agent, or one per group). If it asks for something that only agents have, the run stops and says so.

The pages in this section

  • Model declaration: states, transitions, rates and parameters as objects; how the graph resolves, completes and checks them; and how importers turn another framework’s model into the same objects.
  • Model execution: what sim.init() does, units and time, the order modules run in each step, and the policy on errors, warnings, and notes.
  • Solvers and backends: how the solver is chosen, the engines that run each one, the kernel sets, and the tests that pin each path.
  • Transmission: routes (networks and mixing pools), how one module changes another (ss.modify), deliveries, and results.
  • Randomness: random streams and common random numbers, run identity, and how randomness is handled in fitting.
  • Modules: what a module is, its lifecycle, declared modules beside modules written as code, and how to read the loop.
