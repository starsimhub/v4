Model declaration

🧠0% 🤖100%

A disease written as code, as a class whose step() method changes arrays of agents, can be run but not read: Starsim can’t describe the model, draw it, or run it any other way. A declared disease is instead a set of objects (states, transitions, parameters) that describe the model without running it. Everything else is derived from them: the description, the diagram and equations, the stratified model, the exports to other frameworks, and the engines that run it as an ODE, a stochastic compartmental model, or agents.

This page covers those objects, what Starsim does with them when a module is built, how it fills in what you left out, and how models from other frameworks are turned into the same objects. Model execution covers what happens next. For how to write a disease as a modeler, see Diseases and Writing models.

States and transitions

A state (ss.State) is something a person can be in: a compartment in an ODE, a boolean array over agents in an agent-based run. A transition (ss.Transition) moves people between states, driven by a rate, a dwell time, a branch probability, or a trigger. There are four ways to write a model, and they build the same objects:

import starsim as ss

# Operators: "S goes to I at rate beta times I"
S, I, R = ss.states('S I R')
sir = ss.Disease(
    infection = S >> I @ 0.3 * I,
    recovery  = I >> R @ ss.days(10),
)

# Fully explicit, e.g. for building models in a loop or from another language
S, I, R = ss.states('S I R')
sir = ss.Disease(
    ss.Transition(S, I, rate=0.3 * I, name='infection'),
    ss.Transition(I, R, dur=ss.days(10), name='recovery'),
)

# A class, when there is also behavior that isn't a transition
class SIR(ss.Disease):
    S, I, R   = ss.states('S I R')
    infection = S >> I @ 0.3 * I
    recovery  = I >> R @ ss.days(10)

# A class whose structure depends on its arguments, declared in __init__()
class SIRS(ss.Disease):
    def __init__(self, waning=True, **kwargs):
        super().__init__(**kwargs)
        self.define_states(ss.states('S I R'))
        self.define_transitions(
            infection = self.S >> self.I @ 0.3 * self.I,
            recovery  = self.I >> self.R @ ss.days(10),
        )
        if waning:
            self.define_transitions(waning=self.R >> self.S @ ss.days(100))

The first three are the same model, and give the same results. This is a rule of the design: a keyword means the same thing in every form, and subclassing adds behavior, not vocabulary. A transition takes the state objects themselves, never their names as strings, so nothing is inferred from a name. In the fourth form, what is declared in __init__() is collected as it is given and built once, when the outermost __init__() returns (built_after() in starsim/diseases.py), so a subclass can add to its parent’s states before anything is built; after that, declaring more raises an error.

Rates are expressions

When you write 0.3 * I, nothing is computed. I is a state, so the result is an expression (ss.expressions.Expr, in starsim/internals/expressions.py): a small tree whose leaves are parameters, states, counts (I.n), and properties of people (ss.ppl.age), joined by arithmetic and NumPy functions. Each engine evaluates the same tree in its own terms: a value for each group of a compartmental model, for each agent, or as JAX arrays so a gradient can be taken through the run. This is what lets a model written once be run by any solver.

Two kinds of leaf differ. I.n is the number of people in I, used literally. A bare I means contact with people in I: with no network that’s I.n / N, so beta * I is the textbook beta * S * I / N, and with a network each engine works it out from who actually meets whom, which no single formula can say. Since that is a sum over contacts, a rate must be linear in its bare states (beta * I * I raises a ValueError that suggests the two ways to say what was probably meant). Transmission covers how each engine turns a bare state into a force of infection.

The kind of a transition is derived from its rate, not declared: if the rate mentions a bare state, the transition is contact-mediated and that state is a source of infection; otherwise it is spontaneous. You can see this on the transition itself:

sir.infection.contact     # True: its rate mentions I
sir.infection.terms       # {I: par(0.3)}: the coefficient of each source of infection
sir.recovery.contact      # False

Parameters

A number written inline becomes a parameter of the module, named after its slot: above, sir.pars has beta (the coefficient of I) and dur_I (the dwell time of recovery, the mean time in I), with init_prev. A duration is always named by the state it is the time in, or by its transition if people can leave that state after more than one duration (dur_recovery), and a rate by its transition (rate_death); any other name is qualified by its transition only if two would clash (beta_infection). Wrap a value in ss.par() when it needs a name, bounds, or a source; bounds are what make it fittable, since sim.fit() fits every parameter with bounds to every result with data. A value may also vary by group (ss.by(age=[...])), in time (ss.timeseries()), or between people (a distribution): the slot decides what a value means, and the form is free. Setting a parameter the module doesn’t have raises a KeyError that lists the parameters it does have and suggests the nearest, since a misspelling that is silently ignored is one of the hardest bugs to find. See Parameters.

Dimensions

Age, sex, place, and risk group are all handled by one operation, stratify(), which takes a finished model and divides it by a property of people:

sim = ss.Sim(sir, stratify=dict(age=[0, 15, 65]))   # or sim.stratify(age=...), for every module
sir.stratify(risk=['low', 'high'], adjust={'infection': [1, 3]})  # one disease's own dimension

Stratifying doesn’t copy the states: sir still has S, I, and R, and the dimension becomes an axis. In a compartmental run each state has one row per group; as agents the property is an array on the people, and the groups are used for adjustments, conditions, and results. The base model and the stratification don’t refer to each other, which is what lets one disease be reused with different structures. A stratified result is still one result (res.I.select(age='0-14'), res.I.by('age')). Properties of people are normally stratified on the sim, because every disease has to agree on them. The code is in starsim/dimensions.py (ss.dimensions.Strat), and the groups a sim ends up with are sim.groups. See Stratification.

The graph: resolve, complete, check

When ss.Disease(...) is called, it builds the module’s graph (ss.graph.Graph, in starsim/internals/graph.py). The graph is where the objects you wrote become a model:

  1. Collect and name. It gathers the states, transitions, parameters, and results, and names any that have no name: from the keyword they were passed under, then a name= argument, then the variable they’re bound to in the calling code. A transition with none of these is named infection if it is the disease’s only transmission (as in ss.SIR), and otherwise gets a name built from its endpoints (I_to_R); a state with none raises a ValueError, since a made-up state name would leak into results.
  2. Resolve. It finds which states are people and which are plain counts (a water reservoir, a mosquito population), derives the kind of each transition from its rate, marks the sources of infection, works out which transitions are acquisitions of the disease, and finds the first state (where people start and are born into).
  3. Complete. It turns inline values into named parameters, and groups the exits of each state into those that compete (rates, resolved together in one draw, so declaration order never matters) and those that split on entry (p=).
  4. Check. It checks what can be checked without a sim: the time dimension of every rate, that branch probabilities add up, that exposure is linear, and that keywords name real parameters.

So mistakes in the model’s structure are errors when the disease is built, at the line that made it. What needs the sim (the unit of bare numbers, values against their bounds, the shapes of values by group, the choice of solver) is checked at sim.init().

Picking names up from variables is convenient but implicit, so it happens in one place, once. It can miss (a transition written inline in the call gets the fallback name), and describe() shows the names used.

Guessed defaults

Short models leave a lot unsaid: how a dwell time is distributed, how people mix, how many there are. Starsim fills each gap with a default and records the rule that produced it: a guessed default. describe() prints the resolved model with every guess marked, so nothing is assumed silently:

import starsim as ss

S, I, R = ss.states('S I R')
beta = ss.par(bounds=[0.1, 1.0], source='to be fitted')
sir = ss.Disease(
    infection = S >> I @ beta * I,
    recovery  = I >> R @ ss.lognorm_ex(mean=ss.days(10), std=ss.days(3)),
    init_prev = 0.01,
)
sim = ss.Sim(sir, stop=100)

Every [guessed: ...] is a choice you didn’t make: 10,000 people, the ODE solver, homogeneous mixing, 11 Erlang stages for the lognormal dwell time, and beta starting at the geometric middle of its bounds. Each guess is tested both ways: a model that makes it has it marked, and one that doesn’t, doesn’t.

Ways to write a model out

A Starsim model is written as Python, and that code is the model: it is what is kept, shared, and compared (with a diff in a text editor, or by the results it gives). The other forms each hold less:

What Method Holds Read back?
The code the script itself; for an import, sim.imported.code the model, as Python yes, by running it
Results as JSON sim.to_json() parameters, summary, and results, for use elsewhere no
A saved sim ss.save('run.sim', sim) the sim itself (a pickle), including partway through a run yes, with ss.load()
Another framework’s format ss.export_to(sim, 'odin') or 'sbml' the compartmental form of the declared diseases yes, with ss.import_from()

A sim made in Starsim is never written back out as Starsim code: its code is the script that made it. Only an import is written as code, as the next section explains.

Importers and exporters

Every importer reads another framework’s model into one intermediate object, ss.converters.Source: its states, parameters, flows as rate expressions, stratifications, outcomes, and what it couldn’t translate. One function, ss.converters.write(), writes a Source as Starsim code (a declared ss.Disease, with its parameters, states, and transitions as variables, ending with sim = ss.Sim(...)), by the same rules for every format, and ss.converters.build() runs that code to make the sim. So there is one path, from a foreign model to code to a sim, and never from a sim back to code; each framework needs only a reader, and there are no framework-to-framework converters. The code is kept as sim.imported.code, for the user to keep and change. A value the writer can’t write as code, such as a network, is given by the importer as ss.converters.Code('...'), the Python that makes it.

The hardest part of importing is reading rates. Most frameworks write a flow as a total, such as beta * S * I / N; the importer turns it into a per-person rate on a transition, and says how it read each one. A rate divided by the population total is exposure through the routes (beta * I); one without the division is density-dependent and is kept as a count (beta * I.n); anything else is kept literally, as an expression of counts, which is exact under every solver. A Source can also be filled in by hand, which shows each step:

src = ss.converters.Source('sir', format='by hand')
for name, n in dict(S=990, I=10, R=0).items():
    src.add_state(name, init=n)
src.add_par('beta', 0.3)
src.add_par('gamma', 0.1)
src.add_flow('S', 'I', rate='beta * S * I / (S + I + R)', per='total', name='infection')
src.add_flow('I', 'R', rate='gamma * I', per='total', name='recovery')
sim = ss.converters.build(src, stop=100)
print(sim.imported.code)

import starsim as ss

# Parameters
beta = ss.par(0.3)
gamma = ss.par(0.1)

# States
S, I, R = ss.states('S I R')

# Transitions and outcomes
infection = S >> I @ (beta * I)
recovery = I >> R @ gamma

sir = ss.Disease(
    S, I, R, infection, recovery,
    init_n = dict(S=990, I=10),
    first = 'S',
    name = 'sir',
)

sim = ss.Sim(diseases=[sir], stop=100, total_pop=1000)

if __name__ == '__main__':
    sim.run()
    sim.plot()

The flow beta * S * I / (S + I + R) was read as frequency-dependent exposure, and written as beta * I; gamma * I lost its I and became a rate per person. Exporting goes the other way, from the built model:

print(ss.export_to(sim, 'odin'))
## sir, exported from Starsim 4.0.0; time is in days

An importer keeps the source’s names, marks what it guessed (as [guessed] in describe(), like a hand-written model), keeps going when something doesn’t map onto a built-in piece, and lists what it couldn’t translate by name (ss.errors.ImportIncomplete, also in sim.imported.incomplete). An incomplete import still runs, without the listed parts, and the warning says how to finish it with the import-model skill for AI assistants (in starsim_ai/). Exporters work the other way: SBML and odin are written from the built model (each disease’s graph and engine, in its compartmental form), and each export lists what it left out or changed (ss.errors.LossyExport), one line per declaration. A network, a module written as code, and a function are always listed as left out. ss.converters.to_hub() writes the runs of a MultiSim as a forecast-hub submission.

The code is in starsim/converters/: core.py holds Source, write(), and build(), there is one file per framework, and export.py has the exporters. The files for epydemix, MEmilio, and summer2 also run as scripts in those frameworks’ own environments (needing neither Starsim nor Sciris), where they write the model as JSON for the importer to read; EpiModel’s equivalent is an R script (dump_epimodel.R). Each importer is tested against its framework’s own examples (tests/devtests/io/) and in a scaled-down demo per framework (tests/switching/ in the lingua_franca_design repo). For the modeler’s view, see Import and export and the conversion pages for each framework.

The vocabulary

A language nobody can hold in their head is one nobody uses correctly, so the design record lists every public name in one place (17-vocabulary.md), and a name is added only after asking: does Starsim already have one; can it be written with what exists (a bednet is an ss.modify, a metapopulation a stratification by patch); would more than one kind of model use it; is a keyword enough?

The capitalization rule is Starsim’s existing one: modules, containers, and base classes are CamelCase (ss.Sim, ss.Disease, ss.Vaccine); the pieces you put inside them are lowercase (ss.days, ss.normal, ss.modify, ss.vaccinate). The importers are held to the same vocabulary: they write only names that a person would write by hand, which is why every import is ordinary Starsim code.

Limits

  • Code is opaque. A function given as a rate (rate=my_fn) isn’t analyzed in advance; if it needs something only agents have, a compartmental run stops and says what it asked for.
  • A disease written as code is not data. A disease with its own define_states() of arrays and its own step() runs in the same loop, but describe() shows only its class, arrays, and parameters. A class can mix the two: declared transitions, plus code in step() after super().step(). See Modules.
  • Some things need agents. A distribution across people or an individual-level network has no compartmental form, so solver='auto' runs the model as agents and says why. See Solvers and backends.
  • Exports carry less than the code. Only the compartmental form of the declared diseases goes into odin or SBML.
