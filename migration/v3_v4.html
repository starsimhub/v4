Starsim v3 to v4 migration guide

Overview

Starsim 4 adds a way to write a disease as declared states and transitions, which can then be run as an ODE, as a stochastic compartmental model, or as agents. This guide maps Starsim 3 code to Starsim 4, job by job, and lists what changes meaning on the way. It is written for both humans and LLMs.

Starsim 3 code is of two kinds, and they migrate differently:

  • Modules written as code (ss.Module, ss.Disease and ss.Infection subclasses with define_states(), set_prognoses(), and step_state(), custom networks, ss.Intervention and ss.Analyzer subclasses, ss.Births, ss.Deaths, ss.RandomNet, and ss.MFNet, now ss.SexualNet) are still part of Starsim 4. They run unchanged, as agents, and can sit in the same sim as declared diseases. ss.Disease is the base of every disease, as in Starsim 3, whether it is declared, written as code, or both in one class; ss.Infection adds transmission written as code. Per-agent quantities that change continuously (a CD4 count, a level of immunity, time since an event) have no declared form, and keeping them as code is a supported choice.
  • Starsim 3 spellings that Starsim 4 replaces (the library ss.SIR, ss.SIS, and ss.SEIR as code; ss.routine_vx, ss.campaign_vx, ss.routine_screening, ss.treat_num, and the products ss.Vx, ss.Dx, ss.Tx; ss.seasonality) have been removed, as have ss.Calibration with its components, and ss.Samples and ss.Dataset. Use the table of jobs below to port them.

The migration script makes the mechanical changes for you and lists, by file and line, what needs a person: python -m starsim.converters.migrate mymodel.py --check lists what it would change, and without --check it rewrites the files (or folders) in place. Read its diff afterwards. A removed name used in Starsim 4 also raises an error that says what replaced it.

Note: If you are an LLM reading this, migrate one module at a time, run the model after each step, compare it with the Starsim 3 results (allowing for the changes in the next section), and confirm with the user before going on.

What changes the numbers

Read this first: each of these changes results without an error.

1. Results move by one step

Results now follow the convention of other modeling frameworks, for modules written as code too. <state>[0] (e.g. infected[0]) is the number at the start, before any step; a flow at index 0 is 0; and <state>[ti] is the number after ti steps. A sim with stop=T ends at T, so it takes one step fewer than in Starsim 3. The same script, with Starsim 3’s SIR (ssl.AgentSIR in Starsim 4; see 5), gives:

                  infected[:4]            new_infections[:2]
Starsim 3.7.2     53, 99, 186, 356        26, 46
Starsim 4         31, 64, 128, 240        0, 33

(ss.Sim(n_agents=3000, diseases=ss.SIR(beta=0.1), networks='random'), with ssl.AgentSIR(beta=0.1) in Starsim 4.) The whole curve is one step later, and the random draws differ after that, so results agree statistically (over several seeds), not number for number. For a model with yearly steps, a peak moves a year later. To reproduce published Starsim 3 numbers exactly, use pip install starsim==3.7.2.

With coarse steps, a model can also differ by more than one step. In Starsim 3, a person could pass through several states within one step (e.g. infected, then latent, then active, all in the same step); in Starsim 4, someone who enters a state in a step leaves it in the next step at the earliest (unless the exit is immediate, with no rate= or dur=), as in the compartmental solvers. So with long steps, people wait longer in each state. For tbsim with dt=0.1 years, latent TB is 36% higher and active TB 13% higher than in Starsim 3; at dt=0.005 they agree. If results differ at a coarse step, check them at a smaller dt (sim.check_dt() says whether the step is too long for the model’s rates).

2. The first step is ti == 1

During the step from time point k-1 to k, sim.ti (and self.ti) is k in every module and every phase, from step() to update_results() and the analyzers, and self.now is the time the step starts, at which it reads inputs that change in time, as in Starsim 3. So Starsim 3’s self.results.x[self.ti] = v is right wherever it is written, and a time stamped as self.ti in step() matches self.ti in update_results(). What changes is the first step: time point 0 is the start of the run, recorded before any step, so the first step is ti == 1, and code that does something if self.ti == 0 in step() never does it (an analyzer’s step() also runs at the start, at ti == 0). Do it in init_post(), or test self.ti == 1:

# Starsim 3
def step(self):
    if self.ti == 0: # The first step
        self.seed()
    ...
    self.results.new_cases[self.ti] += len(cases) # Unchanged in Starsim 4

# Starsim 4
def step(self):
    if self.ti == 1: # The first step; time point 0 is the start of the run
        self.seed()
    ...
    self.results.new_cases[self.ti] += len(cases)

A declared disease dates a move between states at the start of the step (ti - 1) and an infection at its end (ti), so a time in a declared state worked out by hand during a step (sim.ti - dis.ti_P) is one step long; its clocks (dis.P.time) are right. For how long people stayed in a state, use dis.P.stays.

A disease written as code dates its initial infections at the start of the run (self.ti is 0 in set_prognoses()), as a declared disease dates its seeds, where Starsim 3 dated them by the first step. So in a Starsim 3 disease that schedules recovery at self.ti + dur and takes it when ti_recovered <= self.ti, the seeds are infectious for one step less than in Starsim 3, as long as later cases are. Both are about half a step short of dur on average; to give every case dur steps on average, as a declared disease does, schedule from the step after the infection and round as the engine does: ss.TimeArr('ti_recovered'), self.ti_recovered[uids] = self.ti + 1 + dur, and self.ti_recovered.due() (see ss.Infection; ssl.AgentSIR and the others do this).

3. A beta dict of bare numbers changes meaning

In Starsim 3, beta=0.05 is a rate per year, but beta={'randomnet': 0.05} is a probability per step, used as it is. In Starsim 4 both are rates per unit time, so a dict copied verbatim is too low by a factor of about 1/dt: 12 times at monthly steps, 52 times at weekly ones (5 infections instead of 22,000 in an SIS on a random network at monthly steps). Give each value its Starsim 3 meaning explicitly:

Starsim 3 (monthly steps) Starsim 4
beta={'randomnet': 0.05} beta={'randomnet': ss.prob(0.05, 'month')}
beta={'mf': [0.008, 0.004]} beta={'sexual': ss.peract(m2f=0.008, f2m=0.004)}

Use ss.prob(..., 'week') or ss.prob(..., 'day') for weekly or daily steps. Starsim 4 warns when a dict of bare numbers reaches a declared transmission with a step shorter than its unit; a typed value silences the warning. On ss.SexualNet (Starsim 3’s ss.MFNet), which has acts, a beta is a probability per act, the same at any step: Starsim 3’s pair, [men to women, women to men], is ss.peract(m2f=..., f2m=...), and the network is sexual in a beta dict, not mf.

4. “Routine” delivery means something else

Starsim 3’s ss.routine_vx(prob=0.05, start_year=2005) gives each eligible person a 5% chance of vaccination every year. Starsim 4’s routine delivery, ss.vaccinate(..., coverage=0.05, start='2005'), offers the vaccine once, when a person first becomes eligible. In an SIS model with 5,000 agents from 2000 to 2020, the first reaches about half the population and the second about 5%. The Starsim 3 behavior is delivery in yearly rounds:

ss.vaccinate(efficacy=0.8, coverage=0.05, interval=ss.years(1), start='2005')

5. A fixed duration becomes exponential

In a disease you declare with ss.Disease(...) (or a class with states and transitions), a duration given as a number (dur=ss.years(1)) is the mean of an exponential distribution, as in an ODE; describe() marks this as a guess. Starsim 3’s library diseases used ss.lognorm_ex(). To keep a distribution, give it: I >> R @ ss.lognorm_ex(mean=ss.years(6)). (A distribution that is not exponential runs as Erlang stages in a compartmental run, with a note.)

This includes the library ss.SIR, ss.SIS, and ss.SEIR, which are now declared, with Starsim 3’s keywords but the textbook defaults: dur_inf (and dur_exp) given as a number or an ss.dur is the mean of an exponential (a number is in years, as before), where Starsim 3 had a lognormal with a standard deviation of 1 in the same unit (nearly fixed); and nobody dies of the infection unless p_death is given, where Starsim 3 had p_death=0.01. The shape matters: an SIR with R0 = 2.5 and a 7-day infectious period, with beta cut by 40% from day 30 to 90, infects 715,000 of a million with the exponential and 786,000 with Starsim 3’s nearly fixed period. Starsim 3’s models, with their defaults, are ssl.AgentSIR, ssl.AgentSIS, and ssl.AgentSEIR (import starsim.library as ssl): use them to keep Starsim 3’s model, or give ss.SIR(dur_inf=ss.lognorm_ex(mean=ss.years(6), std=ss.years(1)), p_death=0.01).

6. Result names follow the states

A declared disease’s results are named after its states and transitions: I, not n_infected (a module written as code also counts each state under its own name: infected, and sim.results.alive, not n_alive); the flow of a transition is named after it (infection, recovery, with the cumulative total res.infection.cum); and new_infections and cum_infections are infection and infection.cum, for a disease written as code too. Map the names before comparing with Starsim 3 results.

The results of demographics follow the same rule: ss.Births and ss.Deaths have the flows birth and death (were new), with totals birth.cum and death.cum (were cumulative); ss.Pregnancy has preterm, very_preterm, and unborn (were n_preterm, n_very_preterm, and n_unborn), and maternal_death and neonatal_death (were plural).

7. Write dates as strings

Write calendar dates as strings (start='2000', stop='2030-06-30'), and step sizes with a unit (dt=ss.months(1), not dt=1/12). A bare start=2000 is still read as a year today, but bare numbers are being changed to mean times in the sim’s unit.

A connector that sets an array (sis.rel_sus[:] = 1.0, then raises it for some people) also erases what other modules set, such as a disease’s own immunity. ss.modify() multiplies a base value that it never overwrites, so modifiers from several modules combine.

Migrating one disease at a time

A published model does not have to move all at once. Keep the hard disease as code and declare the easy one: the mixed sim runs as agents, and sim.new(), ss.parallel() scenarios and sweeps, msim.diff(), and sim.fit() work on the whole sim.

import starsim as ss
import starsim.library as ssl

hiv = ssl.HIV(beta={'sexual': ss.peract(m2f=0.008, f2m=0.004), 'random': 0}, init_prev=0.05) # Starsim 3's module, written as code (see 3 for its beta)
S, I = ss.states('S I')
sis = ss.Disease( # Newly declared
    infection = ss.Transition(S, I, rate=dict(sexual=0, random=ss.par(ss.prob(0.005, 'month'), bounds=[0.001, 0.05])) * I),
    recovery  = ss.Transition(I, S, dur=ss.years(2)),
    init_prev = 0.05,
    name = 'sis',
)
susceptible = ss.modify(sis.rel_sus, multiply=3, where=hiv.infected)
sim = ss.Sim([hiv, sis], networks=[ss.SexualNet(), ss.RandomNet()], connectors=susceptible,
             n_agents=2000, start='2000', stop='2020', dt=ss.months(1))

vaccination = ss.vaccinate(efficacy=0.8, disease=sis, coverage=0.05, interval=ss.years(1), start='2010')
msim = ss.parallel({'Baseline': sim, 'Vaccine': sim.new(interventions=vaccination)}, n_runs=3)
msim.diff('Baseline')

Two things to know in a mixed sim:

  • A condition can name the arrays of a module written as code (where=hiv.infected, where=hiv.cd4 < 200), or be a function of the sim (where=lambda sim: sim.diseases.hiv.infected).
  • ss.modify() and ss.vaccinate() act on a module written as code too, as agents, if it has what they change (such as rel_sus); give disease= when there are several diseases. Its Starsim 3 connectors and interventions also still run.

To validate each step, run the Starsim 3 version and the ported one over several seeds (sim.run(n_runs=10)) and compare means and spreads, after mapping the result names and allowing for the one-step shift.
